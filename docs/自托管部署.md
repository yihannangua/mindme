# 自托管部署

推荐 Node.js 24、SQLite 和 WebSocket 后端；示例使用 Docker Compose 及同机反向代理。此指南面向自己部署的单用户空间，不开放多人注册。

## 配置

复制 `deploy/server.env.example` 为 `deploy/server.env`，替换为自己的 HTTPS 来源和随机密钥。`https://mindme.example` 是示例，不能直接作为真实站点使用。

```bash
cp deploy/server.env.example deploy/server.env
chmod 600 deploy/server.env
node -e "console.log(require('node:crypto').randomBytes(48).toString('base64url'))"
```

将生成值填入 `SESSION_SECRET`。升级时保留原值，不重复生成或替换已有环境文件。

| 变量                      | 用途                                           |
| ------------------------- | ---------------------------------------------- |
| `PUBLIC_ORIGIN`           | 自己的 HTTPS 来源，不含路径、查询参数或凭据    |
| `AUTH_MODE=passkey`       | 推荐认证方式；否则默认 Google 模式需要单独配置 |
| `SESSION_SECRET`          | 至少 32 字符的随机密钥，独立保存，升级时保留   |
| `MIGRATION_REQUIRED=true` | 在显式初始化或迁移完成前阻止业务访问           |
| `MINDME_PORT`             | Compose 对本机暴露端口，默认 3180              |
| `MINDME_RELEASE`          | 本地镜像标记，建议每次升级使用不同值           |

Compose 内部固定使用 `/var/lib/mindme/mindme.sqlite`，数据放在命名卷。不要对已有空间使用 `docker compose down -v`，该操作会删除持久卷。

## 首次部署与 Passkey

```bash
docker compose -f deploy/compose.yaml build
docker compose -f deploy/compose.yaml run --rm --no-deps mindme node dist-server/cli.js passkey-setup --fresh
docker compose -f deploy/compose.yaml up -d
```

保存命令显示的 15 分钟设置令牌，通过 HTTPS 页面完成 Passkey 登记，再将恢复码保存在独立位置。`--fresh` 只允许空库；已有空间切勿重复初始化。首次令牌过期但尚未登记时，运行不带 `--fresh` 的 `passkey-setup` 重新签发。

本地 HTTP 联调方法见[本地开发](本地开发.md)，生产入口必须使用 HTTPS。Passkey 与来源/域名绑定，不要随意更换来源或将一个站点的凭据当成另一站点可用。

## 反向代理

服务默认仅绑定宿主机 `127.0.0.1:3180`。将自己的 HTTPS 站点转发至该地址，保留 WebSocket 升级头；Caddy 和 Nginx 示例位于同目录。示例假设代理运行在宿主机；容器化代理需要按自己的网络拓扑调整 upstream。

Caddy 使用真实 DNS 可达域名并配置证书后访问。已有代理只合并自己的站点配置，避免覆盖同机其他应用。

## 健康与就绪

```bash
curl --fail http://127.0.0.1:3180/api/health
curl --fail http://127.0.0.1:3180/api/ready
```

就绪接口在空库保护状态可能返回 503；这和进程存活检查不同。首次设置后检查 `/auth/session` 的 Passkey 就绪状态，匿名同步请求应被拒绝。`cli inspect` 会读取完整历史，不作为周期性健康检查。

## 一致性备份

```bash
docker compose -f deploy/compose.yaml exec -T mindme node dist-server/cli.js backup /var/lib/mindme/backups/mindme-before-upgrade.sqlite
```

每次使用不同备份文件名，将完成的备份复制到受限的独立存储，并验证能在隔离环境恢复。运行中的 SQLite 应使用一致性备份 API，不能只复制主数据库而忽略 WAL。

完整恢复需要备份库、同一站点来源、原会话密钥和浏览器端未同步内容的保全。界面 JSON 不能替代服务端数据库备份。

## 恢复与回滚

1. 在隔离目录/卷及兼容版本下验证备份完整性；保留当前数据卷和环境文件的独立副本。
2. 停止写入和应用服务，保留当前数据库及 WAL/SHM 文件；将一致性备份还原到新的数据卷，文件权限需允许容器 Node 用户访问。
3. 保留原来源与环境密钥，连接还原后的新卷启动服务，再验证健康、就绪、Passkey 登录和内容；失败时切回保留的原卷。
4. 在自己的真实设备演练恢复后再切换使用，不通过 `--fresh`、重新导入内容 JSON 或删除 IndexedDB 代替恢复。

代码回滚应使用保留的兼容镜像和配置。数据库 schema 不一定随代码回滚；先检查兼容性，必要时还原已验证的备份到新卷，不直接覆盖唯一数据副本。

## 升级

先制作并验证一致性备份，记录当前镜像版本；获取新代码，设置新的 `MINDME_RELEASE` 后重新构建并 `up -d`。保留旧镜像、数据卷和原密钥。核对静态资源、健康、就绪、登录及双设备内容后再结束维护；不要自动清空浏览器数据。

本次准备在本机验证 Node 服务和自动化测试；通用 Compose 需在自己的目标 Docker 主机上进一步验证，详见[发布前检查](发布前检查.md)。
